# Yuriy AI — Система автоматизации юридического приема и исследований

«Yuriy» — это интеллектуальная система для юридических фирм, которая автоматизирует первичный сбор данных от клиентов через Telegram и проводит глубокое исследование законодательства с помощью ИИ перед тем, как передать дело живому юристу.

## 🏗 Архитектура системы

Система построена на базе **микросервисной архитектуры**, что обеспечивает независимое масштабирование ИИ-агентов и интерфейсов.

### Основные сервисы:

1.  **`bot-service`**: Телеграм-бот на базе `aiogram` v3. Служит точкой входа для клиентов. Показывает статус «печатает...» во время раздумий ИИ и использует Inline-кнопки для подтверждения действий.
2.  **`intake-service`**: «Мозг» системы на базе **LangGraph**. 
    *   Ведет диалог с клиентом (Human-in-the-loop).
    *   Использует **Structured Output** для автоматического определения готовности данных.
    *   Проводит автономный поиск по законам через **Tavily API**.
    *   Компилирует итоговое Markdown-досье дела.
    *   Имеет собственную изолированную БД (SQLite) для истории клиентов.
3.  **`lawyer-service`**: Специализированный сервис для работы юриста. 
    *   Предоставляет ИИ-ассистента, который анализирует собранное досье.
    *   Позволяет юристу задавать вопросы по конкретному делу.
    *   Хранит историю переписки юриста с ИИ в отдельной изолированной БД.
4.  **`backend` (Gateway)**: Шлюз для фронтенда. 
    *   Единая точка входа для Dashboard.
    *   Агрегирует данные и сообщения из всех микросервисов.
    *   Управляет WebSocket-соединениями для обновления дашборда в реальном времени.
5.  **`frontend`**: Панель управления юриста на **Next.js 15 (App Router)**. 
    *   Дизайн в стиле Open WebUI.
    *   Трехпанельный интерфейс: список дел, чат с ассистентом, досье дела.

## 🤖 Технологии ИИ

- **LLM**: Aliyun MaaS (Qwen 3.7 Plus) — OpenAI-совместимый эндпоинт.
- **Workflow**: LangGraph (State Machine) для управления сложными цепочками рассуждений.
- **Search**: Tavily SDK для глубокого юридического поиска в интернете.
- **Patterns**: 
    - *Human-in-the-loop*: Прерывание графа для ожидания ввода пользователя или подтверждения отправки заявки.
    - *Structured Output*: Pydantic-модели для получения технических флагов от LLM вместе с текстом ответа.

## 🚀 Быстрый запуск (Docker)

### 1. Настройка переменных окружения
Создайте файл `backend/.env` (используя `.env.example` как образец):

```env
TELEGRAM_BOT_TOKEN=your_token
DASHSCOPE_API_KEY=your_qwen_key
TAVILY_API_KEY=your_tavily_key
LLM_MODEL=qwen3.7-plus
```

### 2. Запуск всей инфраструктуры
```bash
docker-compose up --build
```

После запуска:
- **Дашборд юриста**: `http://localhost:3000`
- **Шлюз (Gateway) API**: `http://localhost:8000`
- **Сервис Агента**: `http://localhost:8001`
- **Сервис Юриста**: `http://localhost:8002`

## 📊 Поток данных (Workflow)

1.  **Intake**: Клиент пишет боту -> `bot-service` -> `intake-service`.
2.  **Logic**: LangGraph анализирует сообщение. Если данных мало, граф ставит `interrupt` и ждет следующего сообщения.
3.  **Ready**: Как только ИИ выставляет флаг `is_ready`, бот показывает кнопку «Подтвердить отправку».
4.  **Research**: После нажатия кнопки граф «размораживается», идет в интернет за законами и формирует досье.
5.  **Lawyer**: Юрист видит дело в дашборде, читает досье и общается с `lawyer-service` для уточнения деталей.

## 🛠 Разработка и расширение

- **Добавление новых вопросов**: Править `services/intake-service/modules/intake/prompts.py`.
- **Изменение логики графа**: Править `services/intake-service/graph.py`.
- **Новые функции в чате юриста**: Править `services/lawyer-service/main.py`.

## 🧪 Тестирование (Angry Tests)

Бекенд-шлюз системы покрыт тестами согласно методологии **«Angry Tests»** (Егор Бугаенко). 

### Концепция
В отличие от классического тестирования, ориентированного на «счастливый путь» (Happy Path), наши тесты — **«злые»**. Их цель не подтвердить, что код работает, а попытаться его сломать. 

**Ключевые принципы:**
- **Отказ от вежливости**: Мы имитируем сетевые катастрофы, таймауты микросервисов (>60с) и ошибки 502/500.
- **Стресс-данные**: Подача невалидного JSON в WebSockets, пустые досье, битые ID и гигантские payload.
- **Мутационное тестирование**: Использование `mutmut` для проверки того, что тесты действительно «убивают» специально внесенные ошибки в коде. Если тест проходит после того, как мы сломали логику — такой тест считается бесполезным.
- **Изоляция**: Все тесты запускаются в Docker и используют строгий мокинг сетевых вызовов через `respx`.

### Запуск тестов (Docker)
Тесты запускаются как независимая единица в изолированном контейнере.

1. **Запуск стандартного набора (pytest + coverage):**
```bash
COMPOSE_PROFILES=testing docker compose run --rm backend-tester
```

2. **Запуск мутационного тестирования (mutmut):**
```bash
COMPOSE_PROFILES=testing docker compose run --rm backend-tester mutmut run
```

*Результаты покрытия кода (Coverage) составляют >90% для критических узлов шлюза.*

### Как писать новые тесты (Angry Guidelines)
При добавлении функционала следуйте этим правилам «злого» тестирования:

1.  **Забудьте про Happy Path**: Если вы написали тест, который просто проверяет `200 OK`, — вы написали «вежливый», бесполезный тест.
2.  **Правило Сетевого Хаоса**: Всегда добавляйте тест на таймаут (`side_effect=ConnectTimeout`) и на ошибку шлюза (`Response(502)`). Шлюз не должен падать с 500 ошибкой, если микросервис недоступен.
3.  **Правило Мусорных Данных**: Если эндпоинт ждет JSON, отправьте ему битую строку. Если ждет ID, отправьте `null` или объект. Проверьте, что система отвечает понятной ошибкой, а не "трейсбеком".
4.  **Убей Мутанта**: После написания теста запустите `mutmut`. Если мутант в вашей новой функции «выжил» — ваш тест недостаточно строгий. Добавьте проверки (`assert`), которые не дадут коду измениться безнаказанно.

**Пример структуры «злого» теста:**
```python
@respx.mock
def test_new_feature_angry_scenario(client, respx_mock):
    # 1. Имитируем катастрофу во внешнем сервисе
    respx_mock.get("/api/data").mock(side_effect=ConnectTimeout)
    
    # 2. Вызываем наш шлюз
    response = client.get("/feature")
    
    # 3. Проверяем, что шлюз выстоял
    assert response.status_code == 502
    assert "Service unavailable" in response.json()["detail"]
```
